## Жёсткие правила
- Даты — дедлайны результата, но запрещено закрывать задачу формально. Не переносить дефект в прод ради даты.
- Ежедневно: проверять SHA, PR, CI, blocker age, зависшие задачи, наличие следующего маленького PR. Если этап просрочен — отметить RED, назначить конкретное исправление, пересчитать критический путь.
- Каждую неделю: итог PASS/FAIL/INSUFFICIENT EVIDENCE, прогресс относительно плана, прогноз релиза, риски, решения для Claude.
- Любая задача: владелец, входные зависимости, артефакт, тесты, дедлайн. Один PR — одна тема; не делать merge/deploy автоматически.
- Параллельно можно вести UI и data adapters после утверждения контрактов. 3.0 имеет отдельную очередь и релизные критерии.
- GitHub Issue #63 — архитектурный аудит. Исполнителю Codex нужно подтвердить фактическое получение задачи; создание issue само по себе не запускает агента.
